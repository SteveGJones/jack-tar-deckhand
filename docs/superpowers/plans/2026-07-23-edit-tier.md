## 1. Summary

The critique loop today re-rolls the WHOLE image every iteration: `iterate-slide` re-runs paperbanana `--continue-run`, and the creative_vision cascade regenerates from a refined prompt. Both discard content the operator already approved and risk fresh regressions on the parts that were fine. The 2026-07-17 PoC proved `mflux-generate-flux2-edit` performs a **targeted edit** on our already-catalogued Klein-4B 4-bit weights at **$0, ~1 min, no new download** ("change sky to sunset orange, keep ships exactly" → sky changed, ships preserved, crisp boundaries).

This plan adds an **edit tier**: a $0 local image-editing action that takes a base image + an instruction and preserves everything the instruction does not name. It slots into the two critique loops as a fourth channel/action alongside the existing regeneration paths, with the edit-vs-regenerate decision made by a **classifier-proposes / operator-disposes** procedure. Cloud edit endpoints are assessed and **deferred** (§8) — the local $0 edit carries the entire economic thesis; a cloud edit costs a full regeneration and is gated identically, so it buys content-preservation but no cost saving and is not worth the new provider surface yet.

**The split:** PR C ships the mflux edit CLI wrapper + catalog representation + `/image-edit` skill + the smokes (which answer the open text-edit / guidance-range / determinism / multi-reference-influence / base-provenance / dimension-behaviour questions). PR D consumes those smoke results to wire the edit channel into `iterate-slide` and the creative_vision cascade, with manifest provenance (edits chain off a parent image), $0 cost telemetry, and F10/F12 gate parity.

## 3. Wrapper support — `jack-tar-mlx` (PR C)

### 3.1 New module `plugins/jack-tar-mlx/src/edit_image.py` [FIRM: D1]

A sibling to `generate_image.py`, NOT a mode flag on it. Rationale:

- The edit argv shape differs materially — it carries one-or-more **reference images** (`--image-paths`), a distinct entrypoint (`mflux-generate-flux2-edit` / `mflux-generate-qwen-edit`), and distinct provenance semantics (the output chains off a parent). Folding it into `generate_image.py`'s `parse_args` / `_build_argv` would thread `if edit:` conditionals through the most heavily reviewed, drift-guarded file in the plugin.
- `generate_image.py` already exposes every shared helper at module scope, so `edit_image.py` reuses them by import with **zero edits to the generate render path**. **Import form (F-01):** `plugins/jack-tar-mlx/src/` has NO `__init__.py`, the skill invokes the wrapper as a script (`python3 "$PLUGIN_ROOT/src/edit_image.py"`), and the plugin's tests import flat via `sys.path.insert` — so a relative `from .generate_image import ...` is unrunnable. Use the **flat import**, which resolves via the script's own directory on `sys.path` in script mode and via the test suite's existing `sys.path.insert` in test mode:

```python
from generate_image import (
    _single_flight_lock, OLLAMA_LOCK_PATH, LOCK_PATH,
    DEFAULT_LOCK_WAIT_TIMEOUT, STALE_LOCK_AGE_SECONDS,
    _resolve_hf_hub_dir, _hf_snapshot_complete,
    _cleanup_partial_output, _weights_missing, _oom_signature,
    _repo_prequantized, MLX_MODEL_REGISTRY,
)
```

(All 12 imported names verified to exist at `generate_image.py` module scope with the claimed semantics. If a packaged-import context ever materialises, the cascade.py-style `try: from .x import … except ImportError: from x import …` dual-path is the sanctioned fallback — but flat-only matches how this plugin is actually invoked today.)

The ONLY change to `generate_image.py` is additive keys on `MLX_MODEL_REGISTRY` (§3.3) so the drift-guard test stays whole.

**CLI surface:**

```
mflux edit_image.py

  --image-paths BASE.png [REF2.png ...]     # >=1 base/reference image (required-and-plural
                                            #   per the real argparse, F-07; see D11/S4)
  --model mlx/flux2-klein-4b                # default; must be image_edit-capable
  --output PATH
                                            # NO --width/--height flags in v1 (S7 ruling,
                                            #   §8.1): output ALWAYS inherits the SOURCE
                                            #   image's dims (omit-to-inherit confirmed
                                            #   exactly, 1408x768 -> 1408x768). Explicit
                                            #   dims differing from the base are a
                                            #   REPRODUCIBLE mflux HANG (>10 min, stalls at
                                            #   step 1/4, leaked semaphore, no output) —
                                            #   a documented non-feature; revisit on a
                                            #   future mflux release.
  --steps INT                               # default: capabilities.edit_render_steps
  --seed INT                                # omitted -> wrapper GENERATES one and records
                                            #   it (F-08, CONFIRMED by S3: unseeded runs
                                            #   leave ZERO trace in stdout/stderr/sidecar)
  --guidance FLOAT                          # default 3.5 = optimal-strong (S2). 1.5 subtle;
                                            #   quality cliff between 3.5 and 6; 10 unusable

  --quantize N
  --lock-wait-timeout SECONDS  --no-lock
  --check-weights
```

**Behaviour, mirroring `generate_image.py` exactly:**

- **Entrypoint resolution:** looks up `MLX_MODEL_REGISTRY[model]["edit_entrypoint"]`. If the entry has no `edit_entrypoint` (e.g. `mlx/z-image-turbo` — mflux ships no z-image edit CLI), exit 1 with `"model <id> is not edit-capable; edit-capable models: <list>"`.
- **`shutil.which(edit_entrypoint)` missing:** exit 1 with `"mflux edit entry point '<edit_entrypoint>' not found — needs mflux >= <ver>; run: uv tool install --upgrade mflux"`.
- **`--steps` ALWAYS present** in the constructed argv (mflux's silent 25-step default trap applies to the edit CLI too — same family). Default is `capabilities.edit_render_steps` (PoC: 4 for klein).
- **NO `--width`/`--height` flags — dims always inherit the source image (F-03 upgraded to a wrapper-contract matter by S7, §8.1).** S7 confirmed omit-to-inherit works exactly (1408×768 base → 1408×768 output) but explicit dims DIFFERING from the base are a **reproducible mflux hang** (>10 min, twice, stalled at step 1/4, leaked-semaphore warning, no output file). The wrapper therefore does not expose dims flags at all in v1: never emitting them is the only behaviour that cannot hang, an edit should preserve its base's dimensions by definition, and resizing is a post-process concern. Explicit dims are a documented non-feature (the hang is the recorded reason); revisit on a future mflux release. `parse_args` rejects `--width`/`--height` as unknown flags (argparse default).
- **Seed always resolved and recorded (F-08, CONFIRMED by S3).** When `--seed` is omitted, the wrapper generates one (`random.randrange(2**32)`), passes it explicitly to mflux, and reports it on stderr as `MFLUX_SEED_USED=<n>` (sibling to `MFLUX_REPO_USED`). S3 proved this mandatory: unseeded runs leave ZERO trace of the seed — stdout, stderr, and the `--metadata` sidecar are all silent/null — while same-seed runs are pixel-identical (max pixel diff 0), so wrapper-side generation+recording is the only way `edit_chain` replay can work. Callers (`build_edit_args` / `record_edit`) persist the reported seed. **Broadened quirk note (S3 new fact):** the null-metadata-sidecar behaviour applies to plain klein GENERATES too (even with explicit `--seed`), not just edits — the catalog's `mflux_metadata_sidecar_null` quirk on `mlx/flux2-klein-4b` is family-wide, and its note should be reworded in T1 to drop any edit-specific framing (metadata is only in the PNG XMP/IPTC, never the sidecar).
- **Timeout (F-11):** the edit subprocess reuses the model's `capabilities.timeout_seconds` (klein 300 s, qwen 900 s) as its default, overridable via `--timeout` — no separate edit-timeout catalog field for now. qwen-edit is heavier than qwen-generate (mflux #420); S6 records an actual edit wall-clock and, if it approaches 900 s, a follow-up adds `edit_timeout_seconds` to the catalog.
- **Nested single-flight lock, SAME order** (ollama-lock then mlx-lock) — the edit drives the same GPU/unified-memory context, so it must serialise against both generate paths. Reuses `generate_image.py`'s `_single_flight_lock` verbatim. [FIRM]
- **`HF_HUB_OFFLINE=1` / `TRANSFORMERS_OFFLINE=1`** hard guard on the subprocess — an edit never triggers a download. The PoC confirmed klein-edit reuses the ALREADY-cached klein-4b weights, so `--check-weights` for an edit reuses the generate weights check (same `hf_repo` / `hf_repo_fallback`).
- **Repo primary→fallback retry** on `_weights_missing`, identical to generate.
- **Partial-output cleanup** on timeout / non-zero / OOM, identical to generate.
- **`MFLUX_REPO_USED=<repo>` on stderr** + output path as last stdout line — identical contract so the bridge's existing OUT_PNG flow needs no new parser.
- **Input validation:** every `--image-paths` entry must exist and be a readable raster; missing base → exit 1 `"edit base image not found: <path>"` (do NOT fall through to a from-scratch generate).

`_build_edit_argv` is the edit analogue of `_build_argv`:

```python
def _build_edit_argv(meta, repo, prompt, image_paths,
                     steps, seed, guidance, quantize, output_path):
    resolved_steps = steps if steps is not None else meta["edit_steps"]
    argv = [meta["edit_entrypoint"], "--model", repo, "--prompt", prompt]
    argv += ["--image-paths", *image_paths]          # required-and-plural (F-07)
    # NO --width/--height, EVER (S7 ruling, §8.1): mflux inherits the
    # source image's dims when they are omitted; explicit dims that
    # differ from the base are a reproducible hang.
    argv += ["--steps", str(resolved_steps),
             "--output", str(output_path), "--metadata"]
    argv += ["--seed", str(seed)]                    # F-08: seed is ALWAYS resolved
                                                     # by the caller (explicit or
                                                     # wrapper-generated) by this point
    if guidance is not None:                         # default 3.5 optimal (S2);
        argv += ["--guidance", str(guidance)]        # 1.5 subtle, >6 degrades
    if not _repo_prequantized(repo):
        q = quantize if quantize is not None else meta["quantize"]
        if q is not None:
            argv += ["-q", str(q)]
    return argv
```

> **[RESOLVED — S2 executed, §8.1]** `--guidance` default 3.5 confirmed optimal-strong; 1.5 = subtle; quality cliff between 3.5 and 6; 10 unusable. The skill docs carry the 1.5–3.5 recommended band.
> **[RESOLVED — S4 executed, §8.1; was CONTINGENT-ON-S4]** a second reference DOES influence output — **strongly**: S4 observed direct **element transfer**, not just style pull (the reference image's own subject — a fox character — was injected into the scene), at ~1.6× wall-clock. D11 SHIPS, with a hard documentation requirement: the edit instruction MUST tightly scope what the anchor/reference image is for (e.g. "match the colour palette and lighting of the second image; do NOT add any subject from it"), and **content leakage from references is a documented failure mode** in the `/image-edit` skill and the creative_vision anchor-usage guidance. The image-reviewer dispatch after a multi-ref edit should explicitly check for injected reference subjects.

## 4. iterate-slide integration (PR D)

### 4.1 The edit channel and where the edit-vs-regenerate decision lives [FIRM: D4]

**Procedure: classifier proposes, operator disposes.** No autonomous edit.

1. When the operator invokes `iterate-slide` on a slide, the SKILL first computes `edit_channel_available(manifest_entry, backend)` (§4.2). If false, the flow is unchanged (paperbanana `--continue-run` or creative_vision channels only).
2. If available, a lightweight **locality classifier** labels the operator's feedback (and, for creative_vision, the Director's Critic verdict) as `local` | `global` | `ambiguous` — with one hard carve-out applied FIRST:
   - **text carve-out (HARD-EXCLUDE, D9/S1)** — feedback targeting in-image TEXT ("fix the third label", "correct the spelling", "the title should read X") NEVER routes to edit, regardless of spatial locality: S1 showed the simplest word→word edit re-garbles ("NOTICE"→"NOBTICE") even while preserving everything else. Text fixes → re-roll (or annotate-figure native mode, which is perfect-text-by-construction). The classifier returns `text_excluded` for these so the SKILL can explain WHY edit is not offered.
   - **local** — bounded NON-TEXT region / single element / colour / lighting: "darken the sky", "make the arrow red", "remove the seagull". → **propose edit**.
   - **global** — composition, subject count, whole-scene restyle, "wrong idea": → **propose re-roll** (existing paths).
   - **ambiguous** → present both, operator picks.
3. The operator **confirms** the channel. For creative_vision, this confirmation IS an F12 gate touch (fires on every iteration regardless — §5.3). For **academic_figure (non-creative_vision) slides** — the only other slide class iterate-slide serves today (F-12) — the edit is $0 and therefore **F10-ungated**, but the operator still explicitly picks the channel (no silent auto-edit).

The classifier is a pure-Python heuristic (`classify_edit_locality`) — keyword/imperative-shape based (region/colour/single-noun cues → local; count/layout/"redo"/"instead" cues → global), returning a confidence. It is **advisory**: `draft` mode uses it to pre-select; `enumerate` mode shows it as an annotation; the operator always confirms. This mirrors the existing `draft`-mode "classify heuristically… confirm routing with operator" contract already in the creative_vision branch of the SKILL.

> **[RESOLVED — S1 executed, FAIL (§8.1); was CONTINGENT-ON-S1]** edits DO re-garble text. The text carve-out above is a **hard exclusion** — not offered-with-warning ("it's $0" does not apply: a garbled label costs operator review time and risks shipping "NOBTICE"). D9 is FIRM.

### 4.3 Manifest / history — edits chain off a parent image [FIRM: D5]

Provenance is the point of an edit — the manifest must record what was edited from what. On the image-manifest entry:

```jsonc
{
  "slide_number": 4,
  "file_path": ".../slide-04-edit-2.png",
  "content_hash": "sha256:new...",
  "backend": "mlx_edit",
  "model_used": "mlx/flux2-klein-4b",
  "cost_usd": 0.0,
  "edit_chain": [
    { "iteration": 1, "parent_content_hash": "sha256:base...",
      "parent_file_path": ".../slide-04-draft.png",
      "instruction": "darken the sky, keep the ships and horizon",
      "edit_args": { "model": "mlx/flux2-klein-4b", "steps": 4,
                     "image_paths": [".../slide-04-draft.png"], "seed": 42 },
      "backend": "mlx_edit", "cost_usd": 0.0, "timestamp": "..." }
  ]
}
```

`record_edit` seeds `edit_chain` on first edit (parent = the pre-edit `content_hash`/`file_path`), appends on subsequent edits, always overwrites top-level `file_path`/`content_hash` with the newest, and keeps `refinement_count` semantics compatible with `update_manifest_entry`. A regeneration (not an edit) does NOT append to `edit_chain` — it starts a fresh lineage (a re-roll replaces the base; the old edit_chain is preserved in history but no longer active). **`edit_args.seed` is ALWAYS present** (F-08): the wrapper resolves a seed for every edit (explicit or generated, reported via `MFLUX_SEED_USED` on stderr) and the SKILL passes the reported value into `record_edit` — an unseeded chain entry is a bug, since klein's null-sidecar quirk would make it unreplayable.

For `annotation_mode: native` slides, the existing `iterate_slide_dispatch.annotation_refresh_required` / `annotation_refresh_notice` guard (T12 of the v2 doc) MUST fire on an edit exactly as it fires on a regeneration — the base_image_hash changes, the AN-01 hash gate would otherwise refuse the overlay. PR D routes the edit through the SAME Step 7.5 refresh guard already in the SKILL. No new guard; a test pins that an edit triggers it.

## 7. Assessment: cloud edit endpoints [FIRM: D7 — DEFER]

Endpoints that exist today:
- **Gemini image editing** — `generate_content` with an input image part (Nano Banana Flash/Pro). Pricing = a full generation: Flash 1K **$0.067**, Pro 1K **$0.134** (catalog `per_resolution`). An edit is NOT cheaper than a regeneration.
- **FAL FLUX edit** (e.g. flux-2 edit/redux endpoints) — tiered-megapixel pricing ~ **$0.03–0.05** for 1K, same order as FLUX generation.

**Recommendation: defer.** Reasoning:
1. **No cost advantage.** A cloud edit costs the same as a cloud regeneration. The entire economic thesis of #143 is the $0 local edit that preserves approved content. A cloud edit preserves content but saves nothing — and under F10 the operator is already paying, at which point "spend to edit" vs "spend to re-roll" is a wash the operator can choose per-render without a dedicated tier.
2. **New provider surface.** It requires an edit path in `jack-tar-cloud/src/generate_cloud_image.py` (image-input `generate_content`), new pricing/quirk rows, retry-decorator coverage, and its own smoke — real cost for marginal benefit right now.
3. **Unbenchmarked quality** on our figure/creative workloads; the 2026-07-17 doctrine says local is adequate for hero/full_bleed and Flash suffices for technical figures — none of which argues for a cloud *edit* tier yet.

**Reserve the seam.** All edit plumbing is provider-agnostic by construction: `backend: mlx_edit` generalises to `cloud_edit`; `record_edit` / `edit_chain` carry no mlx assumptions; `TIER_COSTS` can gain a `cloud_edit_*` entry; `should_fire_operator_gate` already gates any `cost>0` tier. When a future PR E adds cloud edits, it slots in without schema churn. Documented in §10 (out of scope).
